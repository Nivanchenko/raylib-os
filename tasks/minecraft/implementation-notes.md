# Подробности реализации

Это проектные инструкции и опорные фрагменты, **не реализованное демо**. Не копировать весь документ как один `.os`-файл. Использовать разделы в порядке этапов [плана](plan.md); у каждого фрагмента указано место/назначение.

## 1. OneScript и загрузка файлов

- OneScript не выполняет операции над `Структура` как над математическими векторами: `P + D` нужно разложить на X/Y/Z.
- В логических векторах поля **латинские** `X`, `Y`, `Z`; не смешивать их с кириллическими `Х`, `У` из физического примера.
- Экспортные методы классов/модулей помечать `Экспорт`; обработчик класса называется `ПриСозданииОбъекта`.
- Для тригонометрии использовать `Sin`, `Cos`, `Sqrt`, как в `examples/physics/Классы/Вектор.os`. Константа π: `3.141592653589793`.
- `Цел()` отбрасывает дробную часть к нулю, а не округляет вниз. Для координат отрицательного луча нужна собственная функция floor.
- Переменная `И` — ключевое слово BSL; счётчики называются `Индекс`, `Кадр`, `Ось`.
- Headless-тесты используют `#Использовать ".."` из `examples/minecraft/tests/`. Они **не** подключают внешнюю компоненту; состояние в каждом тестовом случае создавать заново.
- На успешный запуск тест печатает только свой итог `...: OK`; при ошибке — `ВызватьИсключение`, ненулевой exit code. Недостаточно напечатать «FAIL» и закончить успешно.

Опорный helper для `ВоксельныйЛуч.os` (такой же принцип допустим в `Мир.os`):

```bsl
Функция Пол(Значение)
    Результат = Цел(Значение);
    Если Значение < Результат Тогда
        Результат = Результат - 1;
    КонецЕсли;
    Возврат Результат;
КонецФункции
```

## 2. Данные мира и кэш

Поля класса `Мир`: приватные `Блоки`, `КэшОткрытых`, `КэшГрязный`; `Перем Версия Экспорт`. Все координаты и ID валидировать до вычисления индекса. Неправильное чтение (включая нецелую координату) возвращает 0. Публичные поля массива не экспортировать.

Инициализировать `Блоки` 2048 нулями, а не массивом из `Неопределено`. Вызовы заполнения сценой использовать через `УстановитьБлок`, чтобы не обходить правила/версию. `Очистить` ставит все ID=0, но увеличивает `Версия` **один** раз, если был хотя бы один непустой блок.

`Версия` — счётчик фактических изменений, а не число кадров. Рендер хранит `ВерсияКэша=-1` и пересоздаёт свои три группы только при несовпадении. Не держать одновременно «всегда обновляемый список» и флаг грязного кэша — это даёт два источника истины.

`ОткрытыеБлоки()`:

```text
если кэш чист: вернуть прежний массив
новый массив = []
для Y=0..7, Z=0..15, X=0..15:
    id = ПолучитьБлок(X,Y,Z)
    если id=0: пропустить
    если любой из шести соседей имеет id=0:
        добавить Структура("X,Y,Z,Тип", X,Y,Z,id)
сохранить массив; отметить кэш чистым; вернуть его
```

Шесть соседей: `(x±1,y,z)`, `(x,y±1,z)`, `(x,y,z±1)`. Тип соседей не важен: вода непрозрачная, она тоже закрывает соседнюю грань. Метод не удаляет отдельные грани: каждый открытый куб целиком рисуется одним `DrawCube`.

## 3. Игрок: числовое состояние

Поля приватные, геттеры возвращают **новые** структуры, чтобы внешний код не мог незаметно изменить состояние. В `ПриСозданииОбъекта(X=8,Y=6,Z=14,Yaw=0,Pitch=-0.349065850398866)` сохранить числа; сразу ограничить Pitch и обернуть Yaw. Тесты могут использовать `Новый Игрок(0,0,0,0,0)`.

Направление и правая ось из плана заданы в правой системе координат: Y вверх; при yaw=0 вперёд `-Z`, вправо `+X`. Вертикальное движение задаётся отдельной осью, не меняется от Pitch.

```text
P = позиция
yaw += DeltaX * 0.0025
pitch = clamp(pitch - DeltaY * 0.0025, -85*π/180, 85*π/180)
пока yaw > π: yaw -= 2*π
пока yaw < -π: yaw += 2*π
D = (sin(yaw)*cos(pitch), sin(pitch), -cos(yaw)*cos(pitch))

F = (sin(yaw), 0, -cos(yaw))
R = (cos(yaw), 0, sin(yaw))
V = F*Вперёд + R*Вправо + (0,Вверх,0)
если длина V > 0:
    P += V / длина V * 4 * clamp(Dt,0,0.05)
```

Не нормализовать нулевой V в «вектор по умолчанию»: при отсутствии клавиш игрок остаётся неподвижным. Ввод W+S/A+D/Пробел+Ctrl взаимно сокращается.

Для создания raylib-камеры в `app.os`:

```bsl
P = Игрок.Позиция();
D = Игрок.Направление();
Камера = Рейлиб.НоваяКамера3D(
    Рейлиб.НовыйВектор3(P.X, P.Y, P.Z),
    Рейлиб.НовыйВектор3(P.X + D.X, P.Y + D.Y, P.Z + D.Z),
    Рейлиб.НовыйВектор3(0, 1, 0), 70, 0);
```

`GetMouseRay` можно использовать позже как диагностическое сравнение центра экрана, но основной DDA не зависит от DLL и не извлекает поля COM-вектора.

## 4. DDA без пробелов в алгоритме

### Результат

Создать helper `Промах()` внутри `ВоксельныйЛуч.os`:

```bsl
Функция Промах()
    Возврат Новый Структура("Попадание,X,Y,Z,NX,NY,NZ,Расстояние",
        Ложь, 0, 0, 0, 0, 0, 0, 0);
КонецФункции
```

Попадание имеет те же поля, `Попадание=Истина`, одну ненулевую компоненту нормали ±1 и расстояние от исходного P. Не возвращать `Неопределено` или разные структуры в разных ветках.

Экспортируемая точка входа модуля — `Трассировать(Мир, Начало, Направление, Дальность=5)`. В OneScript `Найти` — зарезервированное имя встроенной функции, его нельзя объявить как функцию модуля.

### До обхода

1. Если `Дальность<=0`, длина D<0.000000000001 — промах. Иначе нормализовать D.
2. Проверить `Мир.ПолучитьБлок(Пол(P.X),Пол(P.Y),Пол(P.Z))`: если непусто — промах (редактирование в клетке камеры запрещено). При точной целой границе действует это же полуоткрытое владение ячейкой из ТЗ, без специального исключения.
3. Рабочий EPS для сравнения расстояний — 0.000000001; сдвиг точки при выборе начальной клетки — 0.000001. Не использовать один большой epsilon для всех задач.
4. Данные трёх осей хранить в массивах `[X,Y,Z]`: P, D, max=`[16,8,16]`, step, cell, tMax, tDelta. Так логика одинаковая, не нужно копировать три несовместимых ветки.

### Отсечение по миру (slab)

Это псевдокод для `Найти`, где `INF` означает большое положительное число, например 1000000000000000000 (1e18, помещается в числовой тип OneScript):

```text
tEnter=-INF; tExit=INF; входнаяНормаль=(0,0,0)
для осей X,Y,Z в этом порядке:
    если abs(D[ось]) < 1e-12:
        если P[ось] < 0 или P[ось] >= max[ось]: промах
        иначе продолжить эту ось без деления
    a = (0 - P[ось]) / D[ось]
    b = (max[ось] - P[ось]) / D[ось]
    near=min(a,b); far=max(a,b)
    если near > tEnter + EPS:
        tEnter=near
        входнаяНормаль=нулевая с компонентой -sign(D[ось])
    tExit=min(tExit,far)

tStart=max(0,tEnter)
tEnd=min(Дальность,tExit)
если tStart > tEnd + EPS или tExit < 0: промах
cell = floor(P + D*(tStart + 0.000001)) по каждой оси
если cell вне сетки: промах
distance=tStart
normal = входнаяНормаль если tEnter>=0, иначе (0,0,0)
```

Если tStart=0 и normal всё ещё нулевая, но сдвиг через целую границу изменил клетку относительно `floor(P)`, взять `-sign(D)` первой изменившейся оси X/Y/Z. Пример: P.X=2, D.X=-1, воздух в X=2, блок в X=1 → расстояние 0, нормаль +X. На обычном старте внутри воздуха нормаль остаётся нулевой до первого перехода.

### Инициализация переходов

```text
для каждой оси:
    если abs(D[ось]) < 1e-12:
        step=0; tMax=INF; tDelta=INF
    иначе:
        step = 1 если D>0, иначе -1
        boundary = cell+1 если step=1, иначе cell
        tMax = (boundary - P[ось]) / D[ось]
        tDelta = abs(1 / D[ось])
```

Все t — от **исходного** P, не от точки входа в мир. Не смешивать `tStart + tMax` с этой формулой.

### Обход

```text
до 64 итераций:
    если cell вне мира или distance > tEnd + EPS: промах
    если ПолучитьБлок(cell) != 0:
        если normal нулевая: промах
        иначе вернуть hit(cell,normal,max(0,distance))
    next = min(tMax.X,tMax.Y,tMax.Z)
    если next > tEnd + EPS: промах
    normal=(0,0,0)
    для X,Y,Z:
        если abs(tMax[ось]-next) <= EPS:
            cell[ось] += step[ось]
            tMax[ось] += tDelta[ось]
            если normal нулевая: normal[ось] = -step[ось]
    distance=next
после лимита: промах
```

Обновляются **все** совпавшие оси, нормаль выбирается по X/Y/Z. Иначе луч на ребре может ложно выбрать боковую клетку, которой лишь касается. Тестировать одновременно результат, нормаль и расстояние; «выбран какой-то блок» — недостаточно.

## 5. Редактирование: точный порядок проверок

`Выбор` — структура, `Выбор.Попадание` — флаг. Модули возвращают `Новый Структура("Изменено,Причина", Булево, Строка)`; не возвращают текст HUD и не знают про мышь.

**Обе операции:** если флаг ложь, расстояние <0/>5+EPS, координаты цели нецелые/внешние или текущий ID цели=0 → `no-hit`. Это защищает от устаревшего выбора. Удаление дальше просто вызывает запись ID=0, успешный результат `ok`.

**Установка после проверки цели:**

1. ID нецелый или не 1..3 → `invalid-type`.
2. NX/NY/NZ нецелые или сумма их модулей не 1 → `invalid-hit`.
3. `Q=(X+NX,Y+NY,Z+NZ)` вне мира → `bounds`.
4. `ПолучитьБлок(Q)!=0` → `occupied`.
5. Пересечение Q с безопасным кубом камеры → `near-camera`.
6. `УстановитьБлок(Q,ID)`; после успешной записи → `ok`.

Пересечение по X: `Q.X < P.X+0.2 И Q.X+1 > P.X-0.2`; аналогично Y/Z. Все три условия должны быть истинны. Строгое сравнение разрешает точное касание. Для дробных проверок пользоваться допуском 1e-9, не переписывать правило безопасности.

После **одного** действия в кадре пересчитать выбор из текущего мира: иначе удалённая рамка останется висеть на один кадр. Не выбирать следующую цель и сразу применять к ней удерживаемую кнопку.

## 6. Кадровый цикл и ввод

Константы клавиш raylib для адаптера: W=87, S=83, A=65, D=68, Пробел=32, левый Ctrl=341, Tab=258, 1=49, 2=50, 3=51. Кнопки мыши: левая 0, правая 1. Esc по умолчанию закрывает окно через `ОкноДолжноЗакрыться`.

`УправлениеАктивно`, `ПропуститьDelta`, `ФокусБыл` — состояние ввода. При старте захватывать курсор только у окна в фокусе. Обрабатывая Tab, потерю или возврат фокуса, пропускать **весь игровой ввод кадра**, включая клики, чтобы клик активации не разрушал блок.

Последовательность одного кадра:

```text
1. Прочитать фокус, Tab, dt и логические размеры окна.
2. Потеря фокуса -> выключить ввод, EnableCursor.
   Возврат фокуса -> оставить ввод выключенным.
   Tab при стабильном фокусе -> переключить захват; этот кадр пропустить.
3. Если ввод активен и не пропускается:
   прочитать mouse delta (первый после захвата только поглотить)
   повернуть и переместить игрока
   выбрать тип по 1/2/3
4. Получить P/D, построить raylib-камеру.
5. Рассчитать выбор DDA, либо промах при неактивном вводе.
6. Если ввод активен и кадр не пропускается:
   если IsMouseButtonPressed(0): удалить
   иначе если IsMouseButtonPressed(1): поставить
7. Если изменён мир: синхронизировать кэш и пересчитать выбор, НЕ ввод.
8. BeginDrawing -> ClearBackground -> BeginMode3D
   три группы мира -> рамка без shader -> EndMode3D
   HUD -> EndDrawing
9. Собирать метрики, но не сортировать/не печатать каждую клетку каждый кадр.
```

Нулевые размеры свёрнутого окна заменить на 1 только для вычисления HUD; не прекращать обработку событий `EndDrawing`. Для метрик записывать исходный фактический render size, не подменённый единицей.

## 7. Шейдер: минимальный рабочий старт

Следующие два файла — **предлагаемый шаблон** этапа 2, пока не проверенный в Minecraft-рендере. Он не требует UV, текстуры или per-cube uniform; все обязательные uniform используются. Начать с него и проверить ориентацию нормалей на реальном кубе.

`resources/shaders/minecraft/blocks.vs`:

```glsl
#version 330
in vec3 vertexPosition;
in vec4 vertexColor;
uniform mat4 mvp;
out vec3 worldPosition;
out vec4 baseColor;
void main()
{
    // Только DrawCube с мировыми координатами, без model matrix transforms.
    worldPosition = vertexPosition;
    baseColor = vertexColor;
    gl_Position = mvp * vec4(vertexPosition, 1.0);
}
```

`resources/shaders/minecraft/blocks.fs`:

```glsl
#version 330
in vec3 worldPosition;
in vec4 baseColor;
uniform vec3 uLightDirection;
uniform int uMaterial;
uniform float uTime;
out vec4 finalColor;
void main()
{
    vec3 n = normalize(cross(dFdx(worldPosition), dFdy(worldPosition)));
    if (!gl_FrontFacing) n = -n;
    float light = 0.35 + 0.65 * max(dot(n, normalize(uLightDirection)), 0.0);
    float detail = 1.0;
    if (uMaterial == 2)
        detail += 0.08 * sin(worldPosition.x * 3.0 + worldPosition.z * 4.0 - uTime * 1.5);
    finalColor = vec4(baseColor.rgb * detail * light, 1.0);
}
```

Первый вариант использует нормаль по производным, не зависит от `vertexNormal`; если она работает корректно, не усложнять реализацию второй системой нормалей. Если верх оказался тёмным, сначала диагностировать ориентацию/мировые координаты; не подгонять знак света на каждом ракурсе отдельно.

Базовые цвета `НовыйЦвет`: земля `(134,91,55,255)`, вода `(38,126,165,255)`, древесина `(155,112,64,255)`. Позиции/цвета создать в кэше, а не в горячем цикле.

Поздняя детализация этапа 6: земля — небольшой детерминированный шум `floor(worldPosition*12)`; древесина — полосы вдоль Y с вариацией по X/Z; вода — сумма двух волн мировых X/Z и движущаяся яркость. Материалы не должны требовать разных shader-объектов или загрузки ассетов.

Uniform устанавливать через опубликованные методы:

```text
до трёх групп: SetShaderValueVector3(uLightDirection,(0.4,1,0.3))
               SetShaderValueFloat(uTime,Время)
для Тип=1..3:
    SetShaderValueInt(uMaterial,Тип)
    BeginShaderMode
    DrawCube для центров текущей группы в пределах 24 единиц
    EndShaderMode  // сбрасывает накопленную геометрию до следующего uniform
```

Локации получить **один раз** после загрузки. Нет `uMaterial`/`uTime`/`uLightDirection` → тест падает; не обходить проверку потому, что GLSL их «оптимизировал».

## 8. Ресурсы и ошибки

- Сначала подключить DLL; затем создать окно; только затем загрузить shader.
- В логике рендера `СвойShaderСоздан` устанавливается только после проверки обязательных location. Если raylib вернул стандартный shader при ошибке GLSL, не выгружать его вручную.
- Все пары Begin/End закрывать даже при исключении внутри рисования; хранить флаги активного shader/3D/drawing прохода. Нормальный путь тоже сбрасывает эти флаги после End.
- `Завершить` идемпотентен: повторный вызов не выгружает shader дважды.
- В обработчике ошибки сохранить `ОписаниеОшибки()`, закрыть активные проходы, освободить собственный shader, включить курсор, закрыть окно; затем сообщить исходную ошибку. Не потерять её за исключением очистки.
- Если ресурсы ещё не создавались, не вызывать их выгрузку. Не закрывать контекст до shader.
- Headless-тесты никогда не вызывают эти функции и не зависят от доступности GUI.

## 9. Метрики: один определённый сценарий

Создать `examples/minecraft/tests/testPerformance.os` без параметров командной строки. Он последовательно рисует три профиля, каждый: 5 секунд прогрев + 30 секунд сбор, затем печатает результаты и автоматически закрывается. В сумме около 105 секунд; тесту дать timeout не меньше 120 секунд.

1. Исходный мир, фиксированные P/D из ТЗ.
2. Тот же мир после **100 успешных записей**: удалить Y=1, X=0..9, Z=0..4 (50 клеток); поставить древесину Y=7 в тех же X/Z (50 ранее пустых клеток). Это диагностический сценарий, не попытка обойти дальность в пользовательском вводе. Для него допускается непосредственно `Мир.УстановитьБлок`.
3. Очистить сетку, заполнить ID=1 клетки с чётным `x+y+z`; ожидаются 1024 непустых и 1024 открытых куба.

Между профилями синхронизировать кэш и заново прогревать. Движение камеры/ввод выключены; число реально нарисованных кубов брать из результата `Отрисовка.Нарисовать`, а не из объёма сетки.

Собирать `dt` как фактический `GetFrameTime`, **без clamp игрока**. Среднее FPS=`N/sum(dt)`, среднее мс=`1000*sum(dt)/N`. Не усреднять величины `1/dt`: это другая метрика.

p95: отсортировать копию списка dt после окончания профиля, индекс `ceil(0.95*N)-1` с ограничением `0..N-1`; результат умножить на 1000. Для большой выборки используйте сортировку `O(N log N)` (например, quicksort) или `ТаблицаЗначений` со столбцом времени и `Сортировать`. Сортировка вставками допустима лишь для небольших массивов: на быстром GPU число кадров за 30 секунд может превысить 14 тысяч. Не выдумывать метод `Массив.Сортировать`.

Каждая строка отчёта: имя профиля, N, среднее мс, среднее FPS, p95 мс, число кадров >100 мс, минимум/максимум рисуемых кубов, логический/render size. Сведения о GPU взять из raylib-лога. Не утверждать скорость для неизвестной среды.

## 10. Частые ошибки и порядок диагностики

| Симптом | Сначала проверить |
|---|---|
| Тест не видит класс/модуль | `#Использовать`, относительный каталог, `Экспорт`, имя файла |
| Мир/установка смещены на полкуба | Центр `x+0.5`, клетка `[x,x+1)` |
| DDA путает отрицательные координаты | Собственный floor вместо `Цел` |
| Разрушается не блок под прицелом | Собственные P/D и тот же P+D в камере, а не системный курсор |
| Удержание удаляет много блоков | `КнопкаМышиНажата`, не `КнопкаМышиЗажата` |
| Луч иногда пропускает соседний блок | t от исходного P, одновременный шаг при совпадении границ |
| Все блоки выглядят как вода | Uniform изменён до сброса batch предыдущей группы |
| Свет вращается с камерой | Нормали и worldPosition, не view-space |
| Белый мир без GLSL-ошибки в приложении | Стандартный shader после отказа, location обязательных uniform |
| FPS падает при неподвижном мире | Кэш перестраивается каждый кадр, новые COM-векторы, логирование |
| Первый взгляд после Tab прыгает | Не пропущен накопленный mouse delta |
| После ошибки мышь остаётся захвачена | Ветка очистки/флаги созданных ресурсов |

Диагностировать по одному симптому. Не менять одновременно камеру, DDA и индексацию сетки: тогда тесты перестают локализовать причину.
