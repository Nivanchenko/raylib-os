# Передача следующему агенту

Этот документ предназначен в том числе для работы с gpt-6-luna. Он не делает предположений о качестве модели: задача разбита так, чтобы решения, проверки и границы были явными.

## Состояние на момент подготовки

- Созданы документы в `tasks/minecraft/` и реализован **только этап 1**: `examples/minecraft/Классы/Мир.os`, `examples/minecraft/tests/testWorld.os`.
- Headless-проверка `oscript examples/minecraft/tests/testWorld.os` прошла с `World: OK`; shader/GUI/производительность всё ещё не проверены.
- `resources/shaders/minecraft/` пока не создан; не считать renderer/этапы 2–7 начатыми.
- Рабочие примеры raylib уже существуют, в том числе `src/test3d.os`, `src/testShaderMode.os`, `src/waterDemo.os`.
- Подготовка плана не является разрешением немедленно реализовать все этапы. Начать кодирование после соответствующего запроса пользователя.

При подготовке документов проверены импорт `#Использовать ".."`, необязательные аргументы конструктора, экспорт методов, структуры, floor-helper и `Sin/Cos/Sqrt` в отдельном временном OneScript-сценарии. Количества блоков/открытых кубов и 23 случая DDA сверены отдельным Python-эталоном. Эти проверки подтверждают опорные данные плана, **не готовность будущих OneScript-модулей**. Shader-шаблон и его визуальный результат ещё предстоит проверить на этапе 2.

При продолжении сначала сверить эти сведения с рабочим деревом. Если другой агент уже сделал этап, не перезаписывать его и не объявлять отсутствующим; прочитать diff, выполнить его тесты и определить следующий шаг.

## Порядок чтения

1. Корневой `AGENTS.md` — обязательные правила репозитория и проверки.
2. [spec.md](spec.md) — что именно должно получиться и чего добавлять нельзя.
3. [plan.md](plan.md) — последовательность этапов и будущие файлы.
4. Нужный раздел [implementation-notes.md](implementation-notes.md) — конкретный алгоритм текущего этапа.
5. Соответствующие строки [test-cases.md](test-cases.md).
6. [manual-checklist.md](manual-checklist.md) — только после появления GUI-сценария.

Если документы расходятся: функциональный объём задаёт `spec.md`, детальные контракты уточняет `implementation-notes.md`. Не менять одно молча: устранить противоречие до кодирования. Реальные сигнатуры API всегда проверять в `src/raylibos/Raylibos.cs`, а не в C-справочнике `basic_api.md`.

## Первый запрос для нового сеанса

Для следующего запроса этапа 2 пользователь может передать агенту такой текст:

Реализуй только этап 2 из tasks/minecraft/plan.md: ограниченный шейдерный тест, освещение одного/нескольких кубов и ранний замер. Сначала добавь failing-проверку, затем минимальную реализацию. Не начинай этап 3, не меняй публичный API, зависимости, демо воды или ТЗ. Остановись на контрольной точке этапа 2, если корректный свет/производительность не подтверждены.

Далее просить следующий этап отдельно. Если пользователь явно поручит несколько этапов, выполнять их последовательно с проверкой каждого, а не одним большим непроверенным изменением.

## Цикл работы на каждом этапе

1. `git status --short`, diff затрагиваемых файлов; отличить существующую работу от новой.
2. Назвать текущий этап, его выход и список файлов. Не добавлять четвёртый тип блока или «удобную» физику.
3. Создать тест со значениями из `test-cases.md`. Запустить его **до** реализации; убедиться, что падение связано с отсутствующей функцией/поведением, а не ошибкой синтаксиса.
4. Реализовать только нужные функции и экспортные имена. Для следующего этапа сохранить интерфейсы, а не менять их на похожие.
5. Запустить тест повторно и все уже реализованные headless-тесты. Для GUI отдельно выполнить `-check` и реальный запуск.
6. После правки шейдера проверить лог компиляции, uniform location и видимый результат. Не считать белое окно/стандартный shader успехом.
7. `git diff --check`, проверить отсутствие временных файлов и изменений `Raylibos.cs`/пакетов.
8. Краткий отчёт по форме ниже; остановиться на границе этапа, если дальнейшая работа не поручена.

## Когда остановиться и спросить пользователя

- Для продолжения требуется новый метод raylib, другая версия пакета или замена нативной DLL.
- После удаления лишних пересчётов/COM-вызовов не достигается бюджет производительности.
- Свет не работает через согласованный `DrawCube`-путь и fallback по производным.
- Выявлено противоречие ТЗ, которое меняет поведение (например, нужна прозрачная вода/листва/гравитация).
- Найдены чужие правки, конфликтующие с текущим этапом.
- Нет GUI или нужного SDK: сначала выполнить доступные проверки, явно сообщить недоступные; не выдумывать результат.

Не менять размер мира, управление, дальность луча или пороги тестов только ради зелёного результата. Не обходить DDA лучом с шагом 0.1. Не подключать `UpdateCamera` к уже собственной камере. Не вводить `rlgl`/unsafe/меши без отдельного согласования.

## Формат отчёта

```text
Этап: N — название.
Изменены: точные пути.
До реализации: команда, ожидаемая причина падения, фактический exit code.
После: команды тестов/сборки, exit code и значимые результаты.
GUI: что действительно запущено/посмотрено; что не проверено.
Отклонения от ТЗ: нет / перечислить и согласовать.
Следующий шаг: этап N+1; нужен ли ответ пользователя.
```

Отмечать пункты плана выполненными только при свежих проверках. Ручной чеклист не отмечать по одному `-check`. Не делать Git-коммит и не публиковать изменения без поручения.
